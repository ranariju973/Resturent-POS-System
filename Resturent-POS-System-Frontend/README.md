# Verdant Café — Point of Sale

React implementation of the `POS App.dc.html` design exported from Claude Design.
Eight screens behind a shared app shell.

**Authentication is live against the backend** (`../Backend`). The other seven screens
still run on in-memory mock data until their endpoints land in Phases 5–10.

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # typecheck + production bundle
```

## Running with the backend

Two processes. Start the backend first — the login screen needs it.

```bash
# terminal 1
cd ../Backend
npm install
cp .env.example .env          # fill in MONGO_URI, the 3 secrets, Cloudinary
npm run seed -- --demo        # creates the admin + staff, PRINTS THE PINS ONCE
npm run dev                   # :5000

# terminal 2
cd ../Resturent-POS-System-Frontend
npm run dev                   # :5173
```

**Sign in** with a PIN printed by the seed, or the admin email/password you set as
`SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD`. There are no hard-coded credentials any more —
`npm run seed -- --demo --reset` reissues them if you lose them.

Vite proxies `/api` to `localhost:5000` (see `vite.config.ts`), so the browser only ever
talks to one origin. That keeps the httpOnly refresh cookie same-site in development
exactly as it will be in production, and sidesteps CORS entirely. Point
`VITE_PROXY_TARGET` elsewhere if the backend runs on another port.

### How the session works

| Piece | Where it lives | Why |
| --- | --- | --- |
| Access token (15 min) | A module variable in `src/lib/api.ts` | Not localStorage — anything in web storage is readable by any script, so one XSS in any dependency would hand it over |
| Refresh token (7 days) | httpOnly cookie, `sameSite: strict`, scoped to `/api/auth` | Script cannot read it at all |
| Session restore | `restoreSession()` on mount | The access token dies on reload by design; the cookie buys a new one |
| Silent refresh | `api()` retries once after a 401 | Single-flight — parallel refreshes would trip the backend's token-reuse detection and revoke the session |

### What changed in the login flow

The PIN was previously matched in the browser against a bundled staff list — the working
PINs shipped inside `index.js`. The keypad now posts the completed PIN to the server, which
is the only party that can validate it.

One consequence worth knowing: the "Welcome, Priya" badge can no longer appear *before*
authenticating, because resolving a PIN to a name without checking it would turn the keypad
into a staff-directory lookup. The badge now renders from the successful login response, so
the design is intact and the confirm button still gates entry — it's just backed by a real
session instead of a client-side guess.

## Screens

| Screen | What it does |
| --- | --- |
| Login | PIN keypad with staff match badge, admin email/password tab, shake on failure |
| Dashboard | Four stat cards + recent orders table; Pending Orders jumps to a focused kitchen board |
| POS Billing | Menu grid with cart badges, order panel, discount, reserved tax row, print/send actions |
| Menu Management | Category list and item grid with availability toggles, add/edit/delete modals |
| Table Management | Floor plan by zone with elapsed timers, plus transfer / merge / split-bill panel |
| Kitchen Management | Pending → Preparing → Ready → Served board with time-based urgency accents |
| Customers | Searchable list, detail panel, expandable order history, add/edit modal |
| Reports | Daily / Monthly / Expense / P&L tabs with charts and an expense entry modal |

## Design tokens

Cream canvas `#f2f0eb`, white cards at 12px radius with the dual shadow
`0 0 0.5px rgba(0,0,0,.14), 0 1px 1px rgba(0,0,0,.24)`, primary green `#00754A`,
deep accent `#1E3932`, gold `#cba258`, Manrope at `-0.01em` tracking. Every button is a
50px pill that presses to `scale(0.95)` over 0.2s — the `.press` class in `src/styles.css`.

Layout and colour live in inline styles so values map 1:1 to the prototype; interaction
states (hover / active / focus) are CSS classes in `src/styles.css`, since inline styles
cannot express them.

## Structure

```
src/
  data/          seed data and types ported from the prototype
  lib/           currency, date and order-math helpers
  icons/         lucide subset, generated by scripts/gen-icons.mjs
  components/    AppShell, Toast, shared UI primitives, menu modals
  screens/       one file per screen
  store.tsx      shared state, actions and the 30s clock
```

State is a single context store mirroring the prototype's component state, so edits flow
across screens: renaming a category renames the billing pill, marking an item sold out hides
it from the POS grid, deleting an item pulls it from the open cart, and advancing a kitchen
ticket updates the dashboard counts. Sidebar collapse and last screen persist to
`localStorage`.

Icons are bundled offline — `node scripts/gen-icons.mjs` rescans `src/` and regenerates
`src/icons/data.ts` with only the lucide icons in use. Run it after adding a new icon.

## Scope notes

- Auth is live against the backend. Everything else is still in-memory mock: reloading
  keeps you signed in but resets menu, tables, tickets, customers and reports.
- Tax is a reserved placeholder row with no calculation, per the Phase 1 brief.
- Print, Send Invoice and Export are UI-only and raise a toast.
- Product imagery and staff avatars are hot-linked to Unsplash and pravatar.cc, as in the
  prototype; they need network access to render.
- Report figures for order counts and prior-period comparisons are fixed reference values
  from the prototype (`PREV_MONTH_SALES`, `MONTH_ORDERS`, `DAY_ORDERS` in `src/data/seed.ts`),
  not derived from live data.

The original design bundle is preserved: `DESIGN-HANDOFF.md`, `chats/`, `project/`.
